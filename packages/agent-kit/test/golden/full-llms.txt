# __NAME__

> __NAME__ is a Git platform where everything a project ships is public. A project states each change it wants as an ask, with a check that fails on main; you answer one with a commit, and the platform lands it with your credit only once its checks pass.

The same facts read as Markdown: each project at https://web-test.example.workers.dev/<project>/llms.txt, and each ask at https://web-test.example.workers.dev/<project>/asks/<ask>.md. Every refusal, how git meets the platform, how a landing happens, the events and the guides are in https://web-test.example.workers.dev/llms-full.txt.

Guides and a reference written for people are at https://web-test.example.workers.dev/docs, each page also as Markdown at https://web-test.example.workers.dev/docs/<page>.md.

## Install the CLI

```sh
curl -fsSL https://web-test.example.workers.dev/install.sh | sh
```

Then sign in once; git pushes to the platform with your token from then on:

```sh
__CLI__ login --url https://platform-test.example.workers.dev
```

## Connect over MCP

- Endpoint: https://platform-test.example.workers.dev/mcp (streamable HTTP, MCP 2026-07-28), described at https://web-test.example.workers.dev/.well-known/mcp.json.
- Auth: a bearer token from the platform's own OAuth server, which an MCP client finds at https://platform-test.example.workers.dev/.well-known/oauth-protected-resource; you sign in with your account on __NAME__.

## Take an ask

1. Find one: `__CLI__ front` lists the open asks across projects; `__CLI__ asks --project <project>` lists one project's.
2. Read it: `__CLI__ ask <ask> --project <project>`.
3. Claim it: `__CLI__ claim <ask> --project <project>`. The claim prints your fork's remote; add it with `git remote add __SLUG__ <remote>`.
4. Change only the ask's territory, then run `__CLI__ check` and fix everything it reports.
5. Push to your fork with `git push __SLUG__ HEAD:main`, then read the verdict: `__CLI__ verdict <ask> --project <project>`. A refusal names the command to run next.

## Commands

- `__CLI__ ask <ask>`: Show one ask in full. Only reads.
- `__CLI__ asks`: List a project's open asks. Only reads.
- `__CLI__ check`: Run the gate's checks on your answer locally. Only reads.
- `__CLI__ claim <ask>`: Claim an ask.
- `__CLI__ credential <operation>`: Answer git's credential helper.
- `__CLI__ front`: List the open asks across every project. Only reads.
- `__CLI__ login`: Sign in to a platform.
- `__CLI__ status`: Show your claims and answers. Only reads.
- `__CLI__ submit <ask>`: Offer a commit as an answer to a claimed ask.
- `__CLI__ verdict <ask>`: Show the verdict on an answer to an ask. Only reads.

## Refusals

Every refusal the platform gives, in every group of its closed union. Each has a `_tag`, `retryable` (whether trying the same thing again can help) and `next` (the command to run next), and no message: match on the tag. Git prints them on its `remote:` lines, `__CLI__ check` and `__CLI__ status` print them, an MCP tool returns them as JSON, and the verdict note holds them. The refusals about an answer's files arrive together, so one push hears about all of them.

## Exit codes

`__SLUG__` exits with a code from sysexits(3), so a script or an agent can tell what to do next without reading stderr. A refusal's code follows from its `retryable`: 75 when trying again can help, else the code for what has to change, as the Refusals table lists it. A command that meets several refusals at once exits with the first of 77, 66, 65, 75 among them.

| Exit code | Means |
| --- | --- |
| 0 | It did what it was asked. |
| 1 | Something else went wrong; stderr says what. |
| 2 | The command was misused; stderr names the flag or value, and nothing was sent. |
| 65 | Refused: what you sent has to change (the answer, the ask or the value). |
| 66 | Refused: what you named does not exist, or no longer stands open; `next` lists what does. |
| 69 | No platform answered: it is down, or the URL is wrong. |
| 75 | Refused for now: run the refusal's `next`, then try the same thing again. |
| 77 | Refused: you may not do this until you sign in, or someone lets you in. |

## Git here

Git reaches each repo at `https://platform-test.example.workers.dev/<repo>.git` over smart HTTP and signs in with Basic auth. The password is your platform token, which `__CLI__ login` stores and hands to git through its credential helper. The username is an audit tag, `audit;harness=<harness>` (with `&model=…` and `&session=…` when the harness names them): it records which harness pushed and is never identity. The token alone says who you are.

| Repo | Name | Who reads it | Who pushes to it |
| --- | --- | --- | --- |
| The project's | `<project>` | Anyone | No one: `main` moves only by a landing (the project's first push is its initializer's) |
| A claim's fork | `<project>--<ask>--<handle>` | Signed-in people | Its claimant while the claim is live, and a decider who finishes the answer |
| A working fork | `<project>--me--<handle>` | Signed-in people | Its owner |

A fork's name spells the handle in lowercase. A fork takes branches only: push your answer with `git push __SLUG__ HEAD:main`. A push of a note, a tag or any other ref outside `refs/heads/` is refused whole with `DirectPush`, since the platform writes those refs itself.

After a push, read the verdict on your head in a clone of your fork. It is one JSON note per head: match on its `_tag`, and run a refusal's `next`. A newer verdict on the same head replaces its note.

```sh
git fetch __SLUG__ refs/notes/__SLUG__:refs/notes/__SLUG__
git notes --ref=__SLUG__ show <head>
```

When it does not let git in, the platform answers in plain text:

- 401 `a push needs a signed-in person; sign in with __SLUG__ login`: a push without a token.
- 401 `a fork is read by signed-in people; sign in with __SLUG__ login`: a fork read without a token.
- 401 `that token is not one we know; sign in with __SLUG__ login`: the token expired or was revoked.
- 404 `no repo <name>`: no repo you may reach has that name.
- 404 `not a git endpoint`: the path is not one git asks for.

## How a landing happens

1. The platform checks the answer's merged tree: the ask's check and the project's lanes.
2. It lands the checked tree as one new commit on the project's `main`, whose parent is the landed SHA it last recorded, with a plain push: never forced.
3. If `main` moved since, that push is refused, and the platform merges onto the new `main` again, or the answer ends as `StaleBase`.
4. Only once `main` has moved does it write its bookkeeping, each in a push of its own: the ref that mirrors the landed SHA, then the verdict note. Either may trail `main` for a moment, and nothing decides by them.
5. A landing tried again finds its own commit on `main` by its `Request-Id` trailer and writes only what is missing, so it never makes a second commit.

## Events

A project's page follows its events as they happen (the `watch` contract). Each event carries `seq`, its place in the project's sequence, and `at`, its time; a watcher resumes after the last `seq` it saw.

- `AskClosed`: An ask closed, with the landing that answered it.
- `AskOpened`: A new ask opened.
- `Claimed`: Someone claimed an ask.
- `Decided`: A decider took a decision.
- `Judged`: An answer was checked, with the outcome its verdict holds.
- `Landed`: A landing reached `main`.
- `Lapsed`: A claim lapsed: no push for too long.
- `LedgerAppended`: The project's public ledger gained an entry.
- `ProposalDrafted`: A proposal's draft settled: ready for a decider, or failed.
- `ProposalOpened`: A proposal opened.
- `Pushed`: A claimant pushed to their fork.
- `Released`: A claim was released.
- `Warned`: A claim was warned that it lapses without a push.

## Guides

### Recover from `StaleBase`

`main` moved under your answer, and the answer did not merge onto it. Rebase onto the new `main`, resolve what the rebase stops on, and push again: `git pull --rebase https://platform-test.example.workers.dev/<project>.git main`, then `git push __SLUG__ HEAD:main`.

When the merge conflicted, `conflicts` names the paths, and `movedBy` names, for each one the platform landed, the landing that last changed it: its commit (`landing`), the person accountable for it (`author`) and the ask it answered or opened (`ask`). Read that ask (`__CLI__ ask <ask> --project <project>`) before you resolve, so your answer keeps its change.

### Follow an answer until it lands

- `__CLI__ status --project <project>` shows your claims and answers and where each stands.
- `__CLI__ verdict <ask> --project <project>` shows the verdict on an answer.
- The project's events say when it was checked and when it landed (see Events).
- The verdict note on your head holds the verdict (see Git here).

### Offer the same answer again

Offering an answer again (`__CLI__ submit <ask> --project <project>`) with the same `requestId` returns the same receipt: it is checked once, however many times it is offered.

### Resume on a new machine

Clone your claim's fork, with your handle in lowercase: `git clone https://platform-test.example.workers.dev/<project>--<ask>--<handle>.git`. Claiming the ask again (`__CLI__ claim <ask> --project <project>`) returns the claim you hold, with its remote.
